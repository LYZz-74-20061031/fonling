# Fonling 结构化记忆管理器设计

日期：2026-08-13
状态：待用户最终审阅
目标版本：第一版结构化记忆系统

## 1. 背景与目标

Fonling 是面向 Chrome 手机主屏幕使用的个人 AI 剧情聊天网页。现有系统已经具备智能体人设、回复风格、用户身份、角色切换、历史事件、关键信息、当下状态、滚动摘要、JSON 导入导出和 DeepSeek 流式回复等能力。

现有长期记忆主要由用户手动维护，且历史事件、关键信息和当下状态均使用简单字符串。随着单线剧情增长，会出现以下问题：

- 用户需要反复从对话中手动提取重要信息。
- AI 无法主动提示值得长期保留的事件、关系变化和场景变化。
- 字符串数据难以追踪来源、更新旧内容、处理冲突或支撑后续时间线功能。
- 所有逻辑继续写入 `index.html` 会明显增加维护风险。

本项目将建立一个由用户最终控制的结构化记忆中心。AI 可以主动提出候选记忆，但任何候选都必须经过用户确认后才能成为正式记忆。

核心目标：

- 将长期信息划分为历史事件、关键信息和当前场景三类。
- 支持 AI 在剧情发生实质变化时后台生成候选记忆。
- 支持用户确认、修改或不计入每条候选。
- 支持用户主动新增、编辑、归档、失效和删除正式记忆。
- 在剧情请求中只注入常驻和与当前剧情相关的记忆，控制上下文增长。
- 无损兼容现有本地数据和旧版 JSON。
- 将新增功能拆分为独立文件，避免继续扩大 `index.html`。

## 2. 非目标

第一版不包含：

- 剧情存档点或多分支剧情。
- 章节系统、章节摘要和完整时间线界面。
- 人物关系图、好感数值或自动关系计算。
- 语义向量搜索和外部数据库。
- 自动重要度评分。
- 多 AI 角色同时发言。
- 云端同步、跨设备实时同步或自动上传备份。
- 复杂的记忆版本对比界面。

数据结构应允许后续增加章节、时间线和人物关系功能，但第一版不实现这些界面和逻辑。

## 3. 产品原则

### 3.1 用户拥有最终控制权

- AI 只能创建候选记忆，不能直接修改正式记忆或当前场景。
- 每条 AI 候选至少提供“确认记忆”“修改”“不计入”三个操作。
- 用户手动写入的内容立即生效，不需要 AI 再次确认。
- 用户修改后的内容优先于 AI 原始建议。

### 3.2 三类记忆各司其职

- 历史事件回答“已经发生过什么”。
- 关键信息回答“目前长期成立什么”。
- 当前场景回答“故事此刻处于什么情况”。

当前场景始终只有一份，通过字段级更新覆盖。值得长期保留的旧场景变化应另行建议为历史事件，而不是积累多份场景记录。

### 3.3 记忆必须准确、精简、可追踪

- 不把普通动作、重复描写和纯气氛渲染写入长期记忆。
- 不把修辞、猜测和可能性自动写成确定事实。
- 每条正式记忆保留来源、创建方式和时间信息。
- 重复内容应过滤、更新或合并，不应不断追加同义记忆。

### 3.4 记忆功能不得破坏基础聊天

- 记忆分析失败不能影响已生成的剧情回复。
- 新模块加载失败时，基础聊天应尽量继续可用。
- 所有分析结果必须写回发起分析的智能体，不能因用户切换智能体而串数据。

## 4. 架构与文件边界

采用局部模块化，不在第一版彻底重写已经稳定的聊天、角色和导入导出逻辑。

建议新增：

```text
fonling/
├─ index.html
├─ css/
│  └─ memory.css
└─ js/
   └─ memory/
      ├─ memory-model.js
      ├─ memory-analyzer.js
      ├─ memory-ui.js
      └─ memory-controller.js
```

### 4.1 `memory-model.js`

职责：

- 定义正式记忆、候选记忆和当前场景的数据格式。
- 创建稳定且唯一的记忆、候选和消息 ID。
- 提供新增、更新、合并、归档、解决、失效和删除操作。
- 提供旧字符串数据到结构化数据的迁移。
- 提供数据校验、规范化和导入兼容。

约束：

- 不调用 DeepSeek API。
- 不直接操作 DOM。
- 不直接决定什么时候保存 `localStorage`。

### 4.2 `memory-analyzer.js`

职责：

- 判断最近一轮是否可能发生值得分析的剧情变化。
- 构造 DeepSeek 记忆分析请求。
- 解析、校验和清理结构化 JSON。
- 对正式记忆和现有候选进行重复、更新、合并和冲突判断。
- 输出候选记忆，不直接修改正式记忆。

### 4.3 `memory-ui.js`

职责：

- 显示聊天页的“TA 发现了新的记忆”提示条。
- 显示底部候选面板。
- 显示独立记忆中心。
- 提供正式记忆和当前场景的用户操作界面。
- 显示来源、状态、失败提示和本次回复使用的记忆。

### 4.4 `memory-controller.js`

职责：

- 连接聊天主流程、数据模型、分析器和界面。
- 在 AI 回复完成后决定是否启动后台分析。
- 串行化同一智能体的自动分析与手动整理。
- 处理确认、修改、不计入和用户主动写入。
- 调用现有统一保存入口，避免多个模块独立覆盖本地数据。

### 4.5 `memory.css`

仅包含记忆提示条、底部面板、候选卡片、独立记忆中心和模块化场景状态的样式，不重做现有聊天界面的整体视觉风格。

## 5. 数据模型

### 5.1 正式记忆

历史事件与关键信息使用统一对象结构：

```js
{
  id: "memory_xxx",
  type: "history_event",        // history_event | key_info
  content: "阿宁把研究所钥匙交给了主角。",
  status: "active",
  pinned: false,
  sourceMessageIds: ["msg_xxx", "msg_yyy"],
  source: "ai_suggestion",      // ai_suggestion | user | migration
  createdAt: "2026-08-13T...",
  updatedAt: "2026-08-13T..."
}
```

历史事件状态：

- `active`：近期仍可能影响剧情。
- `archived`：已经过去但仍然是历史事实；默认降低注入优先级，相关时仍可再次使用。

关键信息状态：

- `active`：目前仍然成立。
- `resolved`：任务、危机或承诺已经完成。
- `invalidated`：后来证明错误或已被新事实取代。

`pinned: true` 表示常驻记忆，每次剧情请求都应包含。第一版只区分普通和常驻，不引入数值重要度。

为了保证“常驻”语义可信，第一版为全部常驻记忆设置独立的总字符预算 `PINNED_MEMORY_CHAR_BUDGET = 4000`。当新增或修改常驻记忆将超过预算时，界面拒绝保存为常驻并提示用户精简内容或取消其他常驻项；普通记忆不受这个限制。这样已经成功设为常驻的记忆不会在请求中被静默截断。

### 5.2 当前场景

每个智能体只保存一份当前场景：

```js
{
  time: "",
  location: "",
  presentCharacters: [],
  currentGoal: "",
  currentConflict: "",
  characterStates: "",
  environment: "",
  notes: "",
  updatedAt: ""
}
```

AI 可以提出只包含部分字段的 `scenePatch`。确认时只覆盖补丁涉及的字段，未涉及字段保持不变。

### 5.3 候选记忆

```js
{
  id: "candidate_xxx",
  operation: "add",
  memoryType: "history_event",
  content: "建议写入的内容",
  targetMemoryIds: [],
  resultStatus: null,
  scenePatch: null,
  reason: "这是一项会影响后续剧情的承诺。",
  sourceMessageIds: ["msg_xxx"],
  status: "pending",
  createdAt: "2026-08-13T..."
}
```

支持的 `operation`：

- `add`：新增正式记忆。
- `update`：更新一条现有正式记忆。
- `merge`：将多条旧记忆合并为一条。
- `resolve`：归档历史事件，或将关键信息标记为已解决或失效。
- `scene_patch`：字段级更新当前场景。

候选保存在本地，刷新后仍可继续处理。候选本身不会进入剧情请求。

当 `operation` 为 `resolve` 时，`resultStatus` 必须明确为 `archived`、`resolved` 或 `invalidated`，并且必须与目标记忆类型兼容。缺失或不兼容的候选视为无效，不进入待确认列表。

### 5.4 消息 ID

所有新消息包含稳定 ID：

```js
{
  id: "msg_xxx",
  role: "user",
  content: "...",
  _roleName: "阿宁"
}
```

旧消息加载时补充 ID，并在后续保存后保持稳定。正式记忆通过 `sourceMessageIds` 记录来源。

如果来源消息已经被滚动摘要移除，记忆仍然有效，界面显示“来源对话已压缩”，而不是删除记忆或伪造跳转。

## 6. 旧数据迁移和 JSON 兼容

### 6.1 旧本地数据迁移

首次加载旧数据时：

- `historyEvents: string[]` 转为多条 `history_event`，来源标记为 `migration`。
- `keyInfo: string[]` 转为多条 `key_info`，来源标记为 `migration`。
- `currentState: string` 原文放入当前场景的 `notes`，不由系统擅自拆解。
- 缺少 ID 的旧消息获得稳定 ID。
- API Key、人设、回复风格、用户身份、角色列表、当前角色、背景图片、滚动摘要和聊天正文保持不变。

迁移必须先在内存中完成并通过完整性校验，随后才写回。转换或保存失败时不得覆盖原数据。每个智能体独立迁移，一个智能体的数据异常不能阻止其他智能体加载。

### 6.2 JSON 格式

新导出 JSON 增加 `schemaVersion`，并完整包含：

- 结构化正式记忆；
- 当前场景；
- 待确认候选；
- 带 ID 的消息；
- 现有全部智能体设置和滚动摘要。

新版网页支持导入旧版和新版 JSON。导入先进入临时对象并完成校验、迁移和规范化，全部成功后才替换当前智能体的数据。

这里的兼容含义是“新版网页可以读取旧版和新版 JSON”。新版 JSON 不保证能够被尚未升级的旧网页读取。

每个智能体的设置数据增加 `memorySchemaVersion` 和记忆分析元数据。只有 `memorySchemaVersion` 低于当前版本时才运行迁移；成功保存后更新版本号，避免重复迁移。分析元数据至少记录已经完成自动分析的消息 ID 组合，用于保证同一轮不会因刷新而重复分析。

仍保持“一份 JSON 对应一个智能体”的既有语义。

## 7. 交互设计

### 7.1 聊天页提示

采用已经确认的混合方案：

- 剧情回复完成后，若产生候选，在聊天底部显示轻量条状提示：“TA 发现了新的记忆”。
- 提示包含待确认数量。
- 提示不得遮挡聊天输入框或最新消息。
- 点击提示，从底部展开候选面板。

### 7.2 底部候选面板

底部面板只负责处理当前待确认候选，不承担长期记忆管理。

每张候选卡片显示：

- 记忆类型和建议操作；
- 建议内容；
- 简短原因；
- 更新或冲突时的旧内容；
- “确认记忆”“修改”“不计入”三个操作。

关闭面板只表示暂时不处理，候选继续保留。只有明确选择“不计入”或对整批执行“不计入”时才删除候选，以防误滑造成数据丢失。

### 7.3 独立记忆中心

独立记忆中心包含：

- 历史事件；
- 关键信息；
- 当前场景；
- 待确认记忆。

提供：

- 主动新增历史事件或关键信息；
- 修改和删除正式记忆；
- 设置或取消常驻；
- 归档历史事件；
- 将关键信息标记为已解决或失效；
- 恢复归档、解决或失效项目；
- 查看创建方式、更新时间和来源；
- 跳转到仍存在的来源消息；
- 编辑或清空当前场景；
- 手动“整理记忆”。

底部候选面板和独立记忆中心操作同一份数据，不创建两套记忆。

### 7.4 修改候选

点击“修改”后允许调整：

- 记忆类型；
- 内容；
- 是否常驻；
- 要更新或合并的目标记忆；
- 场景补丁中的字段；
- 是否归档或使旧内容失效。

提交按钮变为“保存并确认”，最终保存用户修改后的内容。

## 8. 自动触发与手动整理

### 8.1 自动触发

第一版先使用本地轻量规则判断本轮是否可能存在：

- 时间、地点或在场人物变化；
- 承诺、约定、命令、任务或目标变化；
- 秘密、身份或真相揭示；
- 关系、态度或情绪的明显变化；
- 重要物品的获得、交付、丢失或使用；
- 受伤、死亡、失踪、恢复等人物状态变化；
- 危机的产生、升级或解决；
- 新的世界规则或重要设定。

普通寒暄、重复描写和没有剧情推进的回复不自动调用分析 API。

同一轮消息只自动分析一次。只有在分析请求成功解析并完成候选去重后，才将这一轮标记为“已分析”；失败时记录最近失败状态并允许用户手动重试。分析请求在剧情正文完成并保存后后台进行，不阻塞正文显示。

### 8.2 手动整理

用户可以随时从记忆中心点击“整理记忆”。手动整理绕过本地自动触发判断，直接分析近期对话。

同一智能体的自动分析和手动整理必须串行执行，避免重复候选。

## 9. DeepSeek 记忆分析

### 9.1 分析上下文

分析器接收：

- 最近若干轮原始聊天；
- 现有滚动摘要；
- 当前场景；
- 所有活跃关键信息；
- 最近及可能相关的历史事件；
- 仍待确认的候选。

分析请求不需要回复风格等与事实判断无关的设置。上下文超出预算时，优先保留近期对话、当前场景和活跃关键信息，较旧历史由滚动摘要代表。

### 9.2 输出格式

分析器要求严格 JSON：

```json
{
  "shouldSuggest": true,
  "candidates": [
    {
      "operation": "add",
      "memoryType": "history_event",
      "content": "阿宁将研究所钥匙交给主角，并要求对顾临保密。",
      "reason": "重要道具转移并产生保密承诺。",
      "sourceMessageIds": ["msg_101", "msg_102"]
    },
    {
      "operation": "scene_patch",
      "scenePatch": {
        "currentConflict": "顾临可能返回，钥匙的存在必须被隐瞒。",
        "characterStates": "阿宁仍处于高度警戒中。"
      },
      "reason": "当前危机和人物状态发生变化。",
      "sourceMessageIds": ["msg_102"]
    }
  ]
}
```

输出约束：

- 只记录对话中已明确发生或可靠表达的信息。
- 不擅自补全日期、关系、身份或动机。
- 不记录没有后续价值的普通动作。
- 每次最多产生 3 条高价值候选。
- 无内容时返回空列表。

### 9.3 解析失败

- 首次 JSON 解析失败时，可以进行一次受控提取或格式修复。
- 修复后仍无效则放弃本轮分析。
- 任何解析失败都不得修改正式记忆或当前场景。

## 10. 去重、更新、合并与冲突

AI返回候选后，网页进行二次校验：

- 完全重复：丢弃，不显示提示。
- 含义相同但表述不同：转为更新建议。
- 新内容补充旧内容：转为合并建议，并显示修改前后。
- 与待确认候选重复：合并到已有候选。
- 场景状态变化：只生成必要的字段补丁。

当新内容与旧记忆不能同时成立时：

- 不自动覆盖。
- 显示“记忆冲突”或“可能冲突”。
- 展示现有内容、新内容和建议操作。
- 用户确认后才更新状态或创建新记忆。

如果剧情中可能存在撒谎、误导、推测或未证实信息，候选必须标记为“可能冲突”，不能自行认定旧记忆错误。

确认替代旧关键信息时，旧内容标记为 `invalidated`，新内容成为活跃记忆。若揭露过程本身重要，可以另行确认一条历史事件。

## 11. 正式记忆如何进入剧情请求

剧情请求按以下层级组织：

1. AI 人设和世界设定；
2. 用户身份、回复风格和当前身份角色；
3. 当前场景；
4. 常驻关键信息和常驻历史事件；
5. 与本轮相关的普通关键信息；
6. 相关及近期历史事件；
7. 滚动摘要；
8. 最近保留的原始消息；
9. 用户本轮消息。

当前场景保持精简并完整发送。常驻记忆每次发送。普通记忆通过本地相关性筛选，第一版不为检索额外调用 AI。

结构化记忆的总注入预算为 `MEMORY_CONTEXT_CHAR_BUDGET = 8000` 个字符，其中常驻预算最多占 4000 个字符。剩余预算由当前场景和筛选出的普通记忆按优先级使用。预算按最终发送文本的字符数计算，属于第一版的确定性近似值，不依赖额外的 Token 计算服务。

本地筛选参考：

- 用户本轮消息中的人物、地点、道具和事件词；
- 最近几轮聊天；
- 当前场景的人物、地点、目标和危机；
- 记忆更新时间；
- 历史事件是否近期发生。

超出预算时的优先级：

1. 常驻记忆；
2. 当前场景；
3. 直接命中当前人物、地点或道具的记忆；
4. 最近更新的活跃关键信息；
5. 最近的历史事件。

`resolved` 和 `invalidated` 关键信息默认不发送。`archived` 历史事件默认降低优先级，但在直接相关时仍可选中。

## 12. 可观察性

每次剧情请求记录实际使用的记忆 ID、当前场景版本和是否使用滚动摘要。

消息操作菜单提供“查看本次使用的记忆”，展示：

- 使用的常驻记忆；
- 使用的相关记忆；
- 使用的当前场景；
- 是否使用滚动摘要。

第一版只提供简洁列表，不提供复杂 Token 图表。

## 13. 与现有操作的关系

### 13.1 清空聊天记录

清除：

- 原始聊天消息；
- 滚动摘要；
- 待确认候选；
- 与已清空消息关联的分析进度和本次请求记忆记录。

保留：

- API Key；
- AI 人设和回复风格；
- 用户身份；
- 角色列表和当前角色；
- 正式历史事件；
- 正式关键信息；
- 当前场景；
- 背景图片。

候选必须清除，因为候选仍包含已清空对话的内容；用户已经确认的正式记忆继续保留。

### 13.2 删除智能体

删除该智能体的设置、消息、摘要、正式记忆、候选、当前场景和分析元数据。不得影响其他智能体。

## 14. 数据安全与失败恢复

- 迁移或导入必须在临时对象中校验完成后再替换当前数据。
- 保存失败时保留未确认候选，允许重试。
- API 请求超时或分析失败不影响聊天消息和正式记忆。
- 记忆中心显示“本轮分析失败，可重新整理”，不制造错误候选。
- 来源消息不存在时标记“来源不可定位”。
- 页面刷新后待确认候选仍存在。
- 用户切换智能体后，分析结果仍只写回原智能体。
- 浏览器存储接近上限时提醒用户导出备份，不静默删除旧数据。
- 新模块加载失败时显示记忆功能不可用提示，并尽量维持基础聊天。

浏览器存储预警采用可实际检测的策略：每次保存失败并发现 `QuotaExceededError` 时立即显示阻塞式备份提示；此外在设置/记忆中心打开时估算当前智能体序列化后的数据大小并展示轻量占用信息。第一版不假设浏览器能够提供精确的剩余配额。

## 15. 分阶段实施

### 阶段 1：数据基础

- 创建模块文件和加载边界。
- 定义数据结构和操作函数。
- 为消息增加稳定 ID。
- 实现旧数据迁移。
- 实现新旧 JSON 兼容。
- 暂不接入 AI 分析。

### 阶段 2：手动记忆中心

- 实现独立记忆中心。
- 实现正式记忆增删改、状态与常驻管理。
- 实现模块化场景编辑。
- 验证所有数据可由用户可靠控制。

### 阶段 3：候选审批

- 实现聊天提示条和底部候选面板。
- 实现确认、修改和不计入。
- 实现新增、更新、合并、解决和场景补丁。

### 阶段 4：AI 分析与剧情注入

- 实现自动触发和手动整理。
- 实现 DeepSeek 结构化分析。
- 实现去重、更新和冲突处理。
- 实现相关性筛选和上下文预算。
- 实现“查看本次使用的记忆”。

每一阶段完成后都必须保持原有聊天可用，并运行全部现有回归测试。

## 16. 测试与验收

### 16.1 自动测试

至少覆盖：

- 旧历史事件、关键信息和当前状态无损迁移。
- 旧消息获得唯一且稳定的 ID。
- 新旧 JSON 导入与新格式导出往返一致。
- 用户手动新增、修改、删除和改变记忆状态。
- 常驻记忆始终进入剧情请求。
- 普通记忆按照相关性和近期程度筛选。
- 已解决、失效信息不再默认发送。
- 当前场景字段级更新不清空未涉及字段。
- 候选在确认前不进入正式记忆或剧情请求。
- 确认、修改和不计入正确执行。
- 重复候选被过滤或合并。
- 冲突候选不自动覆盖正式记忆。
- 分析失败不影响聊天回复。
- 切换智能体不串数据。
- 清空聊天保留正式记忆和当前场景，但清除候选。
- 现有清空、导入、滚动摘要、角色改名、SSE 和 PWA 测试继续通过。

### 16.2 Chrome 手机尺寸验收

- 提示条不遮挡输入框和最新消息。
- 底部候选面板可滚动、可关闭。
- 三个主要操作按钮容易点击。
- 记忆中心标签切换正常。
- 当前场景字段在窄屏下可编辑。
- 手机键盘弹出时输入框和操作按钮不被遮挡。
- 刷新、切换智能体和重新进入页面后数据正确恢复。

## 17. 完成标准

第一版完成时，应满足：

- 用户可以完全通过记忆中心手动维护三类记忆。
- AI 能在实质剧情变化后提出少量候选，但不能未经确认修改正式数据。
- 用户可确认、修改或不计入每条候选。
- 当前场景支持字段级更新且始终只有一份。
- 剧情请求包含常驻记忆和与当前剧情相关的普通记忆。
- 旧本地数据和旧 JSON 可以无损迁移。
- 清空聊天、导入导出、角色切换和滚动摘要等既有功能不回归。
- Chrome 手机端交互满足可用性要求。
